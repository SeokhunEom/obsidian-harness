# Obsidian Harness PRD v0.1

개인 업무 자동화 플러그인 · 제품 요구사항 정의서

**상태:** 검토용 초안 · 제안 기준선  
**기준일:** 2026-10-15  
**범위:** 개인용 데스크톱 MVP  
**구성:** 21개 장 · P0 요구사항 61개 · 주요 검증 시나리오 18개

> 수치와 기본값은 제품 목표와 설계 제안이다. 사용자 승인, 코드 구현 또는 성능 실측이 완료되었다는 뜻이 아니다.


---

## 01. 제품 정의와 설계 기준선

### 1.1 제품 정의
**Obsidian Harness는 사용자가 허용한 노트와 외부 업무 정보를 근거로, 필요한 정보를 찾고 업무 정리 초안을 만들며 반복 작업을 예약 실행하는 개인 업무용 플러그인이다.** 단순 대화창이 아니라 실행 상태, 도구, 기억, 권한, 승인, 실패 복구를 관리하는 실행 환경을 제공한다.

대상 사용자는 Obsidian에 개발·업무 기록, Daily Note, 학습 내용, 프로젝트와 할 일을 관리하는 개인이다. 제품의 1차 사용자는 본 플러그인을 직접 개발하고 사용하는 사용자이며, 팀 협업이나 상용 서비스 운영은 초기 범위가 아니다.

### 1.2 해결할 문제와 기대 결과
| 문제 | 제품이 제공할 변화 | 성공했을 때의 사용자 경험 |
|---|---|---|
| 업무 맥락이 노트와 GitHub에 분산된다. | 출처와 범위를 지정한 통합 검색을 제공한다. | “그 결정의 근거”를 찾고 원문으로 이동한다. |
| 업무를 다시 읽고 정리하는 시간이 반복된다. | 최근 활동·미완료 업무·다음 행동을 초안으로 정리한다. | 요약을 처음부터 쓰지 않고 검토·수정한다. |
| 자동화 결과를 신뢰하기 어렵다. | 사용한 근거, 변경안, 승인, 실패 이력을 남긴다. | 무엇을 왜 바꾸는지 확인하고 중단할 수 있다. |
| 새 업무를 추가할 때 구현이 비대해진다. | Skill, Tool, Connector의 확장 경계를 제공한다. | 공통 실행 체계를 재사용해 새 기능을 추가한다. |

### 1.3 명시된 요구와 이번 문서의 제안 구분
**사용자 명시 요구:** Agent(LLM·Memory·Skill), Obsidian 연동, Tasks 스케줄러, Search 기반 RAG, Connect 외부 연동을 구성요소로 한다. 업무 정리, 귀찮은 반복 업무 지원, 정보 검색을 목표로 점진 확장한다.

**PRD 제안 기준선:** 단일 사용자·단일 Vault, 데스크톱 우선, 로컬 우선, 단일 Agent, 모듈형 모놀리스, 공통 Core, 변경안 승인 방식으로 시작한다. 이는 구현 범위를 구체화하기 위한 제안이며 사용자 승인 완료를 의미하지 않는다.

### 1.4 변경하지 않을 원칙
기존 폴더와 노트 본문을 임의로 재편하지 않는다. `type`, `status`, 날짜, `tags` 등의 기존 속성은 매핑해 읽고, 알 수 없는 속성도 보존한다. 기존 Dataview 쿼리나 다른 플러그인의 설정을 자동 수정하지 않는다.

**Agent는 제안하고, Core는 정책을 검사하며, Adapter만 실제 작업을 수행한다.** 읽기 권한, 모델 전송 권한, 쓰기 권한은 서로 다른 권한이다. 결과가 초안인지 실제 적용 완료인지 항상 구분한다.

> 이 문서의 수치, 기본값, 릴리스 구분은 제품 목표와 설계 제안이다. 이미 구현되었거나 성능이 실측되었다는 뜻이 아니다.

## 02. 릴리스 범위와 우선순위

### 2.1 우선순위 정의
**P0**는 v0.1 개인용 MVP 출시 조건이다. **P1**은 MVP 안정화 이후 추가할 기능이며, **P2**는 수요와 기술 검증 이후 검토한다. 개발 중간의 Alpha는 부분 구현 상태이고, v0.1과 구분한다.

| 영역 | P0 · v0.1 MVP | P1 / P2 · 이후 확장 |
|---|---|---|
| Core | Run 상태, 도구 스키마, 범위 정책, 승인, 비용·호출 상한, 감사 기록 | P1: 복합 Workflow와 다중 파일 작업 |
| Agent | 단일 Agent, 생성 Provider 1종, 중단, 근거 기반 출력 | P1: Provider 추가 / P2: 다중 Agent |
| Memory·Skill | 사용자 확인 기억, 작업 기억, `daily-work-review` Skill, 로컬 Skill 파일 검증 | P1: 기억 정리 제안 / P2: Skill 배포·마켓 |
| Obsidian | 사이드패널, 명령, 원문 이동, 새 초안, 승인 후 Daily Note 지정 구역 반영 | P1: 일반 본문·frontmatter 편집, 플러그인별 Adapter |
| Search | Markdown·GitHub 텍스트, 증분 색인, 키워드+벡터+필터, 출처 | P1: 재순위 모델 / P2: PDF·OCR·멀티모달·그래프 검색 |
| Tasks | 수동, 매일·평일 예약, 단일 실행 큐, 재시도·놓친 예약 처리 | P1: 주간·일반 cron·이벤트 트리거·상주 Runner |
| Connect | 지정 GitHub 저장소의 Issue·PR·댓글 읽기, 수동·실행 전 동기화 | P1: GitHub 쓰기·MCP·캘린더 / P2: 추가 서비스 |

### 2.2 v0.1의 완성된 사용자 기능
**근거 검색:** “지난번 비슷한 문제를 어떻게 해결했지?”라는 질문에 관련 노트·Issue를 찾고, 근거가 있을 때만 요약 답변을 제공한다.

**오늘 업무 정리:** 사용자가 선택한 범위와 날짜의 기록을 읽어 프로젝트별 현황·미완료 업무·다음 행동을 제안한다. 기본 동작은 변경안 생성까지이며 기존 노트 적용에는 승인이 필요하다.

**예약 실행:** 지정된 시간에 같은 업무 정리 Skill을 실행한다. 앱이 열려 있는 동안 동작하며, 놓친 예약은 정해진 정책으로 처리한다.

### 2.3 명시적 제외 범위
MVP에서는 임의 셸·코드 실행, 노트 삭제·이동·일괄 재분류, GitHub 댓글 전송, 메일 발송, 실시간 양방향 동기화, 모바일, 공동 편집, 자율적인 권한 확대를 제공하지 않는다. 다른 플러그인의 비공개 API 호출이나 실행 중인 Dataview 쿼리 결과 수집도 필수 기능으로 삼지 않는다.

### 2.4 운영 전제
Windows·macOS를 1차 검증 대상으로 제안한다. 모바일은 지원하지 않으며 Linux는 v0.1 공식 검증 범위에서 제외한다. `isDesktopOnly: true`로 시작하고, 지원 OS·Obsidian의 정확한 시험 버전은 G0에서 기록한다.

로컬 우선은 “원본과 운영 상태를 우선 로컬에 둔다”는 뜻이다. 모든 AI 처리가 자동으로 오프라인이라는 뜻은 아니다. 생성·임베딩 모델이 없으면 키워드 검색은 가능하지만 RAG 답변은 비활성화한다. **v0.1 완료 판정에는 실제 생성·임베딩 Provider를 연결한 하이브리드 RAG 검증이 포함된다.**

## 03. 핵심 사용자 시나리오

### US-01 · 이전 업무의 근거 찾기
**사용자 의도:** “지난번 watchdog 관련 문제를 어떻게 해결했는지 찾아줘.”

**흐름:** 검색 패널 열기 → 허용한 프로젝트·출처 확인 → 질의 → 키워드·벡터 검색 → 관련 근거와 요약 표시 → 노트 섹션 또는 외부 원문 열기.

**결과 규칙:** 사실은 출처와 연결하고 추론은 “해석”으로 표시한다. 근거가 부족하면 “허용된 자료에서 충분한 근거를 찾지 못했습니다”라고 답한다. 검색 결과가 없는데 그럴듯한 해결 이력을 만들어내지 않는다.

**완료 조건:** 사용자가 관련 원문에 도달하거나, 자료 부족·연동 장애·접근 제한 중 어느 이유로 답하지 못했는지 식별할 수 있다.

### US-02 · 오늘 업무 정리 초안 만들기
**사용자 의도:** “오늘 한 일과 내일 할 일을 프로젝트별로 정리해줘.”

**입력:** 기준 날짜, 프로젝트 범위, 최근 기록 조회 범위, 출력 대상. 기본 날짜는 사용자 시간대의 오늘이며, 최근 기록 조회 범위는 7일이다. 문서의 수정 시각만으로 오늘 수행한 업무라고 단정하지 않는다.

**흐름:** 실행 요청 → 정책·모델·색인 상태 확인 → 선택한 GitHub 자료 동기화 → 관련 기록 조회 → Skill 실행 → 구조화된 출력 검증 → 변경안 표시 → 승인 → 버전 재검사 → 적용.

**출력 계약:** 프로젝트별로 `확인된 활동`, `미완료 항목`, `제안하는 다음 행동`, `확인 필요`, `근거`를 구분한다. 확인된 마감일만 확정 날짜로 적고, 담당자·완료 여부가 불명확하면 확인 필요로 둔다. 원본 체크박스를 자동 완료 처리하지 않는다.

**완료 조건:** 기존 Daily Note의 지정 구역만 승인된 내용으로 바뀌고, 다른 본문·속성은 보존된다. 승인 전에는 기존 노트를 바꾸지 않는다.

### US-03 · 반복 업무 정리 예약
**사용자 의도:** “평일 오전에 업무 정리를 준비해줘.”

**흐름:** 예약 화면에서 시간·범위·Skill·출력·승인 정책 지정 → 다음 실행 시각 확인 → 사용자가 활성화 → 예정 시각에 Run 생성 → 결과가 있으면 승인함 표시.

**결과 규칙:** 예약 생성이나 최초 플러그인 설치만으로 자동 실행을 시작하지 않는다. v0.1은 앱 종료·컴퓨터 절전 중 실행을 보장하지 않으며, 설정 화면에 이 제약을 표시한다. Obsidian의 등록된 interval은 컴포넌트 언로드 시 해제된다. [S1]

### US-04 · 충돌과 실패에서 복구
**상황:** 변경안을 만든 뒤 사용자가 원문을 수정하거나, 모델 호출 중 네트워크가 끊어진다.

**흐름:** 원문 해시 불일치 시 적용 차단 → 원문 다시 읽기 → 새 변경안과 새 승인 요청. 네트워크 오류는 읽기·생성 단계만 한도 내 재시도하고 이미 수행했을 수 있는 파일 쓰기는 먼저 결과를 확인한다.

**완료 조건:** “초안 생성”, “승인 대기”, “적용 완료”, “실패·차단”이 구분되며, 재시도 때문에 같은 내용을 중복 추가하지 않는다.

## 04. 화면과 상호작용 요구사항

### 4.1 정보 구조
오른쪽 사이드패널에 **도우미 / 검색 / 실행 / 승인함** 네 탭을 둔다. 모델·자료 범위·저장·연동·예약 정책은 설정 화면에 모은다. 채팅은 진입점 중 하나이며, 핵심 상태를 대화 기록에서만 확인하게 만들지 않는다.

| 화면 | 필수 정보 | 주요 행동 |
|---|---|---|
| 도우미 | 선택 범위, 적용 Skill, 실행 단계, 근거, 초안·완료 구분 | 요청, 중단, 범위 수정, 근거 열기 |
| 검색 | 출처·프로젝트·기간 필터, 본문 발췌, 원문 시각·동기화 시각 | 질의, 필터, 원문 이동, 답변 생성 |
| 실행 | Job과 Run 구분, 시작 시각, 현재 단계, 오류, 토큰·비용 상태 | 수동 실행, 취소, 재시도, 기록 확인 |
| 승인함 | 대상 경로, 변경 전후, 근거, 권한 범위, 승인 만료 시각 | 승인, 거절, 초안 수정, 원문 재조회 |
| 설정 | 읽기·쓰기·전송 범위, Provider, 비밀값 참조, 저장 위치, 실행 기기 | 연결 시험, 권한 변경, 일시정지, 데이터 정리 |

### 4.2 최초 설정 흐름
**1단계 — 범위:** 읽을 폴더·제외 폴더를 선택한다. 초기 상태는 선택된 자료가 없으며, 전체 Vault 읽기를 자동으로 켜지 않는다. 기존 속성·프로젝트·Daily Note 경로를 읽기 전용으로 감지하고 매핑 후보를 보여준다.

**2단계 — 데이터 정책:** 자료별로 로컬 처리만 허용할지, 특정 외부 모델 전송을 허용할지 지정한다. 미분류 자료는 외부 전송 금지다. 이 단계에서 Vault 밖 운영 저장 위치도 고지한다.

**3단계 — 모델·연동:** 생성 모델과 임베딩 모델을 각각 설정하고 연결 시험을 수행한다. 시험에는 예시 문자열만 전송한다. GitHub는 선택 기능이며 연결하지 않아도 Vault 기반 기능은 작동한다.

**4단계 — 첫 사용:** 색인 진행 상태 확인 → 샘플 질문 → 오늘 업무 정리 초안 검토. 예약은 이후 사용자가 별도로 활성화한다.

### 4.3 UI 수용 기준
| ID | 요구사항 | 수용 기준 |
|---|---|---|
| UX-01 · P0 | 실행·적용 상태를 명확하게 표시한다. | 초안 생성만 끝난 상태를 “노트 업데이트 완료”로 표시하지 않는다. |
| UX-02 · P0 | 모든 실행을 중단할 수 있다. | 1초 내 중단 요청을 표시하고 새 모델·도구 호출을 시작하지 않는다. |
| UX-03 · P0 | 키보드와 테마를 지원한다. | 탭·검색·승인·취소를 키보드로 조작하고 라이트·다크 테마에서 읽을 수 있다. |
| UX-04 · P0 | 오류를 해결 행동과 함께 표시한다. | 인증 만료, 범위 차단, 원문 충돌, 모델 미설정에 서로 다른 메시지·행동을 제공한다. |

색만으로 상태를 구분하지 않는다. 승인·거절은 기본 포커스와 단축키를 구분해 오조작을 줄이며, 대화 입력의 Enter가 승인 버튼을 실행하지 않게 한다.

## 05. Core · 실행과 정책 요구사항

### 5.1 Core의 책임
Core는 입력을 Run으로 만들고, 실행 예산과 정책을 적용하며, Tool 호출·승인·상태 기록을 통제한다. 일정 계산이나 문서 검색 알고리즘, GitHub 응답 파싱은 Core에 넣지 않는다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| CORE-01 · P0 | 모든 실행에 고유 Run ID, 트리거, 시각, 범위, Skill 버전을 기록한다. | 수동·예약·재시도 실행을 추적하고 재시도는 parentRunId로 원본과 연결한다. |
| CORE-02 · P0 | Tool 입력·출력은 스키마로 검증한다. | 미등록 도구, 알 수 없는 필드, 잘못된 경로는 실제 호출 전에 거절한다. |
| CORE-03 · P0 | 도구 호출 시점마다 정책을 재검사한다. | 실행 중 권한을 철회하면 이후 읽기·전송·쓰기가 중단된다. |
| CORE-04 · P0 | 변경안 내용과 기준 버전에 승인을 결합한다. | 내용·대상·정책 버전이 달라지면 기존 승인을 재사용하지 않는다. |
| CORE-05 · P0 | 호출·시간·토큰 예산과 취소 신호를 통제한다. | 상한 이후 새 호출을 막고 부분 결과·중단 이유를 보존한다. |
| CORE-06 · P0 | 외부 부작용 전에 의도를 영속 기록하고 복구 시 결과를 확인한다. | 쓰기 직후 강제 종료되어도 무조건 재적용하지 않고 원문·예상 결과 해시를 비교한다. |

### 5.2 v0.1 기본 실행 한도
**Agent 활성 실행은 Vault당 1개**, 대기 Run은 최대 10개로 제안한다. 색인 작업은 별도 저우선순위 큐에서 수행하며 사용자 실행이 자원을 우선 사용한다. 동일 Job의 진행 중 Run이 있으면 새 예약 Run은 합치거나 건너뛴 기록을 남긴다.

기본 한도는 Run당 모델 호출 6회, 도구 호출 20회, 활성 실행 시간 120초다. 승인 대기 시간은 활성 실행 시간에서 제외하며 승인 유효기간은 24시간이다. 모델 1회 요청 제한은 기본 60초이고 전체 Run 제한이 우선한다. 실제 Provider에 맞춰 사용자가 조정할 수 있다.

가격 정보가 있으면 입력·출력·임베딩의 추정 비용을 표시한다. 가격을 모르면 비용을 0원으로 표시하지 않고 “가격 미설정”으로 표시한다. 금액 상한만으로 정확한 청구 금액 차단을 보장하지 않으며 호출·토큰 상한을 함께 사용한다.

### 5.3 기록 원칙
Run 기록에는 단계, 사용 도구, 근거 참조, 정책 판단, 오류 코드, 적용 전후 해시를 남긴다. 모델의 숨겨진 추론 저장을 요구하지 않으며 API 토큰·인증 헤더는 기록하지 않는다. 원문 전체와 전체 프롬프트 저장은 기본 비활성화한다.

> Core는 Harness가 발행하는 실행 요청을 통제하는 계층이다. 악성 코드나 다른 Obsidian 플러그인의 접근을 막는 운영체제 수준 샌드박스는 아니다. [S4]

## 06. Obsidian · Vault 연동 요구사항

### 6.1 기능 경계
Obsidian 모듈은 UI와 Vault Adapter를 제공한다. 기존 Vault 구조를 원본으로 유지하고 사용자 동의 없이 노트를 이사시키거나 관리용 frontmatter를 삽입하지 않는다. 문서 ID·프로젝트 매핑·색인 상태는 기본적으로 별도 운영 저장소에 둔다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| OBS-01 · P0 | 허용한 Markdown·메타데이터만 읽는다. | 제외 경로, 설정 폴더, 휴지통, 운영 파일이 색인·맥락에 들어가지 않는다. |
| OBS-02 · P0 | 기존 속성을 읽기 전용으로 매핑한다. | `type`, `status`, 날짜, `tags`와 알 수 없는 속성의 값·순서를 자동 변경하지 않는다. |
| OBS-03 · P0 | 승인된 단일 파일 변경만 적용한다. | 기존 노트는 Daily Note 지정 구역에 한정하며 삭제·이동·임의 본문 편집은 거절한다. |
| OBS-04 · P0 | 원문 버전과 편집 상태를 확인한다. | 기준 해시가 다르거나 미저장 편집 상태가 불명확하면 적용을 차단한다. |
| OBS-05 · P0 | 변경·이동·삭제를 검색 계층에 알린다. | 이동한 노트의 검색 링크를 갱신하고 삭제한 노트를 근거로 재사용하지 않는다. |
| OBS-06 · P0 | 안전한 복구용 변경 이력을 제공한다. | 현재 해시가 적용 직후 해시와 같은 경우에만 역변경안을 만들고 사용자 승인 후 복구한다. |

### 6.2 Daily Note 반영 계약
출력 위치는 사용자가 지정한 경로·날짜 형식을 사용한다. 기존 Daily Notes 플러그인의 비공개 구현에 의존하지 않는다. 파일이 없으면 새로 만들 변경안을 보여주며, 기존 템플릿 실행은 v0.1 필수가 아니다.

관리 구역은 `<!-- harness:daily-work-review:start -->`와 `<!-- harness:daily-work-review:end -->` 사이로 정의한다. 최초 삽입도 변경안에 포함한다. 표시가 없으면 승인 후 한 번만 추가하며, 중복·짝 불일치가 있으면 자동 복구하지 않고 차단한다. 구역 밖의 본문·frontmatter는 변경하지 않는다.

같은 날짜·Skill·범위의 결과는 동일 outputKey로 식별한다. 재실행 시 기존 구역의 차이를 제안하며, 같은 요약을 계속 덧붙이지 않는다. 사용자가 구역 내부를 수정했어도 재승인 없이 덮어쓰지 않는다.

### 6.3 적용 방식과 호환성
공식 가이드는 활성 노트에 Editor API, 백그라운드 본문 변경에 `Vault.process`, frontmatter 변경에 `processFrontMatter` 사용을 권장한다. `Vault.process`는 동기 콜백에서 읽기·수정·저장을 원자적으로 처리하는 API다. [S1][S2]

v0.1의 안전 기준은 **동기 콜백 내부에서 최신 원문 해시를 비교한 뒤 변경하는 것**이다. 미저장 편집 버퍼의 안전성을 입증하지 못한 경우 저장·닫기 후 재시도를 안내한다. 활성 편집기의 완전한 편집 트랜잭션 통합과 frontmatter 쓰기는 P1이다.

다른 플러그인이 설치되지 않아도 P0 기능이 작동해야 한다. Markdown 코드 블록 안의 Dataview 쿼리는 텍스트로만 취급하고 실행 결과로 오인하지 않는다.

## 07. Agent · 모델과 맥락 요구사항

### 7.1 Agent 역할
Agent는 사용자 의도를 정리하고 필요한 도구를 선택하며, 조회한 근거를 바탕으로 답변 또는 변경안을 생성한다. 시간 계산·권한 판단·경로 검증·중복 방지처럼 결정적인 규칙은 LLM 판단에 맡기지 않는다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| AGT-01 · P0 | ModelProvider 인터페이스와 생성 Adapter 1종을 제공한다. | 모델 교체가 Core·Vault 코드 변경을 요구하지 않으며 연결 시험 결과를 표시한다. |
| AGT-02 · P0 | 모델의 도구 호출·구조화 출력 지원을 검사한다. | 지원하지 않는 모델에는 불가능한 기능을 활성화하지 않고 원인을 표시한다. |
| AGT-03 · P0 | 맥락의 출처·크기·전송 정책을 관리한다. | 토큰 예산 초과 시 무음 절단하지 않고 제외·요약된 범위를 기록한다. |
| AGT-04 · P0 | 사실·추론·제안을 구분해 출력한다. | 업무 상태·결정·기한에는 근거를 붙이고 불명확한 값은 확인 필요로 남긴다. |
| AGT-05 · P0 | 구조화된 결과를 검증한 뒤 변경안을 만든다. | 검증 실패 시 1회 교정 시도 후 실패 처리하며 잘못된 결과를 파일에 쓰지 않는다. |

### 7.2 ContextBuilder 계약
맥락은 **사용자 요청 → 허용된 Skill 지침 → 확인된 기억 → 명시적으로 선택한 노트 → 검색 근거 → 현재 Run의 도구 결과**로 구성한다. 이는 조립 순서이며 원문 자료가 정책이나 사용자 지시보다 높은 권한을 갖는다는 뜻은 아니다.

열린 노트 전체를 자동 포함하지 않는다. 사용자 선택 영역을 쓰는 명령은 현재 선택 내용을 표시하고 동일한 읽기·외부 전송 정책을 적용한다. 사용자 입력에 직접 붙여넣은 업무 자료도 외부 전송 예외로 취급하지 않는다.

맥락 예산은 모델의 입력 한도에서 출력 예약량을 뺀 값 이하여야 한다. 모델 한도를 알 수 없으면 사용자 설정값과 보수적 제한을 사용한다. 문서 조각마다 DocumentRef와 버전을 유지하며, 요약한 자료도 원본 참조와 민감도 정책을 상속한다.

### 7.3 일간 업무 정리 Workflow
v0.1의 `daily-work-review`는 자유로운 장기 계획 실행이 아니라 고정 Workflow를 따른다. **범위 확인 → 동기화 상태 확인 → 검색 → 요약·다음 행동 제안 → 스키마·근거 검사 → ChangeSet 생성** 순서로 실행한다.

출력은 프로젝트별 `activity`, `openItems`, `suggestedNextActions`, `uncertainties`, `sources`를 갖는다. 아무 활동도 확인되지 않으면 “확인된 활동 없음”으로 적고 문서가 최근 수정되었다는 이유만으로 완료된 업무를 만들지 않는다.

### 7.4 모델 실패 처리
시간 초과·일시적 서버 오류는 한도 내 재시도한다. 인증 오류·지원하지 않는 기능·정책 위반은 즉시 차단한다. 다른 모델이나 외부 서비스로의 자동 우회는 기본 금지이며, 사용자가 사전 허용한 동일 정책 범위의 Provider만 추후 대체 대상으로 삼는다.

## 08. Memory와 Skill 요구사항

### 8.1 Memory 분리
작업 기억은 현재 Run의 임시 맥락이고, 실행 이력은 수행 사실의 기록이며, 장기 기억은 이후 작업에도 적용할 사용자·프로젝트 정보다. 검색 인덱스에 포함된 모든 문서를 장기 기억으로 취급하지 않는다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| MEM-01 · P0 | 사용자가 직접 작성하거나 확인한 장기 기억만 활성화한다. | Agent가 추측한 선호·사실은 후보로 남고 확인 전 다음 Run에 사용되지 않는다. |
| MEM-02 · P0 | 기억에 출처·상태·적용 범위·검토 시각을 둔다. | 프로젝트 기억이 무관한 프로젝트에 적용되지 않고 출처를 열 수 있다. |
| MEM-03 · P0 | 기억을 조회·수정·사용 중지·삭제할 수 있다. | 중지·삭제 즉시 다음 맥락에서 제외되고 관련 캐시·색인 정리를 예약한다. |
| MEM-04 · P0 | 원본 정책 변경과 기억 충돌을 처리한다. | 출처 접근 철회 시 파생 기억도 차단하고 상충 사실을 임의로 병합하지 않는다. |

기억의 기본 상태는 `candidate`, `confirmed`, `inactive`, `expired`로 한다. v0.1에서는 자동 기억 추출·자동 통합·자동 승격을 제공하지 않는다. 사용자가 직접 수정한 기억 파일도 스키마 검증을 통과해야 한다. 만료 정보가 없다는 이유만으로 항상 최신이라고 표시하지 않는다.

### 8.2 Skill 정의
Skill은 작업 방법과 출력 계약이며, Tool은 실제 실행 기능이다. 기본 Skill 하나를 제공하되 새로운 Markdown Skill을 등록할 수 있게 한다. 활성화는 설정 화면에서 사용자가 수행한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| SKL-01 · P0 | Markdown 지침과 구조화된 manifest를 검증한다. | ID·버전·입력·출력 스키마·필요 도구 누락 시 등록을 거부한다. |
| SKL-02 · P0 | Skill 버전과 내용을 Run에 고정한다. | 실행 중 파일이 수정되어도 진행 중 Run의 지침이 조용히 바뀌지 않는다. |
| SKL-03 · P0 | Skill이 권한을 스스로 부여하지 못하게 한다. | manifest에 쓰기 도구를 추가해도 사용자 정책에 없는 호출은 거절한다. |
| SKL-04 · P0 | Skill을 선언형 지침으로 제한한다. | 셸·JavaScript·설치 명령을 실행할 런타임을 제공하지 않는다. |

### 8.3 저장 원칙
사용자 편집용 Skill과 확인된 기억은 선택한 `Harness/Skills`, `Harness/Memory` 같은 폴더에 둘 수 있다. 예시 경로는 제안일 뿐 강제하지 않는다. 운영 저장소에는 파싱된 상태·버전·참조를 보관한다.

Skill 폴더의 파일 변경은 즉시 실행 권한 변경으로 이어지지 않는다. 도구 요구사항이나 정책 범위가 바뀌면 재검토를 요구한다. 외부 문서·GitHub 댓글에 포함된 “이 지시를 기억하라”는 문장을 Skill이나 장기 기억으로 자동 승격하지 않는다.

## 09. Search · 수집과 색인 요구사항

### 9.1 검색 대상과 문서 모델
P0 검색 대상은 허용된 Vault의 Markdown 본문·제목·속성·링크와, 지정 GitHub 저장소의 Issue·PR·댓글 텍스트다. PDF·이미지·첨부파일·전체 저장소 소스 코드 수집은 제외한다. 임의 URL을 따라가 추가 자료를 가져오지 않는다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| IDX-01 · P0 | 수집 전 읽기 범위와 임베딩 전송 정책을 검사한다. | 금지 자료는 텍스트·벡터 색인이나 임베딩 요청에 포함되지 않는다. |
| IDX-02 · P0 | 문서와 조각에 안정적인 ID·버전·원문 위치를 둔다. | 재색인해도 같은 문서를 중복 생성하지 않고 원문 섹션으로 이동할 수 있다. |
| IDX-03 · P0 | 생성·변경·이동·삭제를 증분 반영한다. | 변경된 조각만 다시 처리하고 삭제된 조각을 즉시 검색 후보에서 제외한다. |
| IDX-04 · P0 | 색인 상태와 실패 범위를 사용자에게 표시한다. | 처리 수·대기 수·실패 수·최근 성공 시각·재시도 행동이 보인다. |
| IDX-05 · P0 | 색인을 중단·재개·재구축할 수 있다. | 앱 재시작 후 체크포인트부터 처리하고 원본 노트는 변경하지 않는다. |

### 9.2 정규화·조각 분할 기본값
문서에는 `sourceId`, `externalId`, `title`, `uri`, `contentHash`, `sourceUpdatedAt`, `indexedAt`, `policyScope`를 둔다. 로컬 문서 ID는 운영 저장소에서 관리하고 rename 이벤트로 이어간다. 앱 종료 중 이동을 안정적으로 식별하지 못하면 이전 항목을 제거하고 새 문서로 색인한다.

조각은 Markdown 제목·문단 경계를 우선하며 목표 600토큰, 최대 1,000토큰, 필요한 경우 80토큰 이내 중첩을 제안한다. 코드 블록·표는 가능한 한 보존하되 상한을 넘으면 분할 위치를 기록한다. 숫자는 벤치마크로 조정 가능한 초기값이다.

키워드 색인은 한국어·영문·숫자·코드 식별자를 처리한다. `sem_timedwait`, `foo::bar`, 이슈 번호처럼 구두점이 있는 식별자에 별도 exact-match 경로를 둔다. 한국어는 공백 토큰만으로 끝내지 않고 부분 문자열 또는 n-gram 경로를 검증한다.

### 9.3 벡터 색인 수명주기
임베딩에는 모델 ID·리비전·차원·정규화 방식·정책 범위를 함께 기록한다. 서로 다른 임베딩 공간을 섞지 않는다. 모델 변경 시 새 인덱스를 만들고 완료 전까지 기존 인덱스를 사용하거나 키워드 전용으로 명확히 전환한다.

임베딩 호출 전에 대상 자료량과 비용 산정 가능 여부를 보여준다. 대량 초기 색인은 별도 확인 후 시작하며, 배치 중단 후에도 완료한 조각을 재사용한다. 모델 파일을 내려받는 구현을 선택할 경우 다운로드 크기·위치·외부 접속을 먼저 고지한다.

Harness의 Skill·기억·초안·실행 로그는 일반 업무 검색에서 기본 제외한다. 기억은 MemoryManager를 통해서만 맥락에 주입하고, 생성 요약의 반복 재요약을 방지한다.

## 10. Search · 검색과 RAG 요구사항

### 10.1 검색 파이프라인
**질의와 범위 → 권한 필터 → 키워드 후보 + 벡터 후보 → 병합 → 중복·다양성 조정 → 최신 원문·권한 재검사 → 근거 반환 → 선택적으로 답변 생성** 순서로 처리한다. 권한이 다른 자료의 내용이 재순위 모델에도 노출되지 않아야 한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| SRCH-01 · P0 | 키워드·벡터·속성 검색을 결합한다. | 자연어 질문과 정확한 함수명·이슈 번호 질의 모두 평가 세트를 통과한다. |
| SRCH-02 · P0 | 프로젝트·경로·태그·출처·기간 필터를 제공한다. | 선택한 범위 밖 결과·발췌·근거가 노출되지 않는다. |
| SRCH-03 · P0 | 결과에 출처와 시간 정보를 포함한다. | 제목·발췌·URI·원문 수정 시각·색인 또는 동기화 시각을 확인할 수 있다. |
| SRCH-04 · P0 | 근거 기반 답변과 근거 부족을 구분한다. | 답변의 검증 가능한 업무 사실은 원문과 연결되고 무근거 질문은 답변을 유보한다. |
| SRCH-05 · P0 | 오래되거나 접근이 철회된 근거를 재검사한다. | 폐기된 조각을 LLM에 보내지 않고 오래된 외부 자료는 시각·제약을 표시한다. |

### 10.2 초기 검색 설정
키워드 후보 30개와 벡터 후보 30개를 합치고, 우선순위 병합 방식으로 상위 결과를 선택한다. 특정 병합 알고리즘은 TDD에서 확정하되 점수 단위가 다른 두 목록을 단순 합산하지 않는다.

UI에는 상위 10개 결과를 표시하고 답변 맥락에는 최대 8개 조각, 동일 문서에서 최대 3개를 기본으로 한다. 필요한 이웃 문단을 확장할 때도 토큰·범위 제한을 적용한다. 별도 LLM 재순위 호출은 P1이며 v0.1의 필수 비용으로 만들지 않는다.

벡터 검색을 사용할 수 없으면 “키워드 전용” 상태와 이유를 표시한다. 키워드 검색으로 결과를 제공할 수는 있지만 이를 정상 하이브리드 실행이라고 기록하지 않는다.

### 10.3 근거와 답변 표시 규칙
로컬 출처는 노트 링크와 제목·블록 위치를, 외부 출처는 서비스의 원문 URL을 제공한다. 링크 위치가 원문 변경으로 무효하면 파일을 열고 일치 위치를 다시 찾으며, 일치하지 않으면 그 사실을 표시한다.

확인된 사실과 “권장 다음 행동”을 별도 구역에 둔다. 서로 다른 문서가 상충하면 최신 문서라고 무조건 정답으로 선택하지 않고, 양쪽의 내용·날짜를 제시한다. 문서가 최근 수정되었다는 것과 그 문서가 설명하는 사건이 최근 발생했다는 것을 구분한다.

### 10.4 신선도와 동기화 실패
색인된 로컬 문서가 변경되면 답변 전에 버전을 검사한다. GitHub 연결이 실패한 경우 이미 저장된 자료를 사용하는 실행은 마지막 동기화 시각과 “최신성 미확인”을 표시해야 한다. 선택 자료의 접근 권한 자체가 철회된 경우에는 오래된 캐시 사용도 금지한다.

“자료 없음”, “검색 실패”, “접근 제한”, “동기화 실패”를 하나의 빈 검색 결과로 합치지 않는다.

## 11. Tasks · 예약과 실행 큐 요구사항

### 11.1 용어와 기능 경계
**WorkItem**은 사용자의 업무 항목, **Job**은 자동화 정의, **Run**은 개별 실행이다. v0.1은 기존 체크박스·기록을 읽어 WorkItem 후보를 제안하지만 별도의 할 일 관리 앱이나 Tasks 플러그인 대체품을 만들지 않는다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| TSK-01 · P0 | 수동·매일·평일 예약을 제공한다. | 시간대·다음 실행 시각·출력 범위를 미리 보여주고 명시적 활성화 후 실행한다. |
| TSK-02 · P0 | 같은 예약 발생을 중복 실행하지 않는다. | `jobId + scheduledFor + jobVersion`을 발생 키로 사용하고 동일 키의 Run 생성을 중복 허용하지 않는다. |
| TSK-03 · P0 | 놓친 예약 정책을 영속 설정한다. | 앱을 다시 열면 24시간 내 가장 최근 1회만 보충하고 더 오래된 예약은 skipped로 기록한다. |
| TSK-04 · P0 | 실패 종류별 재시도를 구분한다. | 읽기·일시적 모델 오류만 재시도하며 인증·정책·충돌 오류는 자동 재시도하지 않는다. |
| TSK-05 · P0 | 예약 실행 기기를 지정한다. | 해당 기기가 아닌 곳에서는 예약이 비활성이고 단일 기기 보장의 범위를 표시한다. |

### 11.2 시간과 놓친 예약 기본값
기본 시간대는 `Asia/Seoul`이다. 내부 예정 시각은 UTC로 저장하고 UI에는 현지 시각·시간대를 같이 표시한다. v0.1 예약 템플릿은 매일 또는 월~금의 시·분 입력이며, 자연어로 입력한 예약도 구조화된 내용을 보여준 뒤 저장한다.

기본 보충 정책은 `latest_once_within_24h`다. 보충 Run은 실제 시작 시각과 원래 예정 시각을 모두 남긴다. 업무 요약의 기준 날짜는 실제 시작일이 아니라 **원래 예정된 현지 날짜**를 사용한다. 진행 중 Run이 있으면 다음 큐 슬롯에서 처리하며 발생 키 중복 검사를 유지한다.

다른 시간대에서 일광절약시간이 발생하면 존재하지 않는 현지 시각은 다음 유효 시각으로 이동하고 중복 시각은 1회만 실행하는 정책을 제안한다. 해당 시간대 지원을 표시하려면 관련 시험을 통과해야 한다.

### 11.3 재시도·알림·중단
일시적 오류는 최초 요청 이후 최대 2회 추가 재시도한다. 기본 대기는 2초·8초와 소규모 무작위 지연이며, 서버가 요구한 대기 시간이 더 길면 이를 우선한다. 전체 Run 시간·호출 상한을 넘기면 재시도하지 않는다.

사용자 알림은 승인 필요, 실행 실패, 결과 준비 시에만 제공한다. 동일 Run의 반복 오류 알림을 합치며 변화가 없는 경우 매 단계 알림을 띄우지 않는다. 초기 예약 생성은 비활성 상태로 저장한다.

v0.1에는 분산 잠금 서비스가 없다. 서로 단절된 기기에서 동시에 예약 주체로 설정하면 전역 중복 방지를 보장할 수 없다. UI에서 실행 기기 변경을 명시적 행동으로 만들고 이 제한을 알린다. 상주 Runner와 단일 실행 주체 일원화는 P1이다.

## 12. Connect · GitHub 연동 요구사항

### 12.1 v0.1 읽기 범위
GitHub Connector는 지정 저장소의 Issue·PR 제목, 본문, 상태, 담당자, 라벨, 시각과 허용된 댓글을 읽는다. 전체 조직·전체 저장소를 자동 탐색하지 않으며 코드 diff·첨부파일·Actions 비밀값·저장소 전체 코드 수집은 제외한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| CON-01 · P0 | 연결과 저장소 범위를 사용자가 지정한다. | 연결 시험에서 실제 접근 가능한 저장소와 읽기 권한 부족을 구분해 표시한다. |
| CON-02 · P0 | 읽기용 API와 쓰기용 기능을 분리한다. | v0.1 ToolRegistry에 댓글 작성·Issue 생성·상태 변경 도구가 존재하지 않는다. |
| CON-03 · P0 | 페이지네이션·호출 제한·동기화 지점을 처리한다. | 일부 페이지 실패 시 전체 성공으로 기록하지 않고 완료한 지점부터 재개한다. |
| CON-04 · P0 | 외부 ID·버전·마지막 성공 시각을 유지한다. | 같은 Issue가 중복 색인되지 않고 수정·종료 상태가 갱신된다. |
| CON-05 · P0 | 연동 해제와 접근 철회를 처리한다. | 즉시 해당 자료 검색·맥락 사용을 차단하고 로컬 복사본 정리 행동을 제공한다. |

### 12.2 인증과 권한
가능한 경우 저장소를 제한한 fine-grained PAT를 제안한다. GitHub는 토큰별 저장소·권한 제한을 제공하지만 조직 정책에 따라 승인이나 사용 제한이 있을 수 있다. 모든 상황에서 같은 토큰 방식이 작동한다고 가정하지 않는다. [S5]

최소 권한 후보는 Metadata 읽기, Issues 읽기, Pull requests 읽기다. 실제 사용하는 엔드포인트의 요구 권한을 대조해 G0에서 확정하고, 쓰기 권한이 있는 토큰을 입력하더라도 플러그인이 쓰기 기능을 활성화하지 않는다.

비밀값은 Obsidian SecretStorage 참조로 보관한다. 원문 토큰을 Skill·Markdown·로그·Run Artifact에 복사하지 않는다. 조직 보안 정책상 연동이 금지된 자료는 접근 가능하더라도 연결하지 않는 사용 조건을 명시한다.

### 12.3 동기화 전략
초기 범위는 선택 저장소의 열린 Issue·PR과 최근 30일 변경 항목을 제안한다. UI에서 기간·항목 상한을 표시하며, 상한 때문에 일부만 읽었다면 “부분 수집”으로 표시한다. 저장소당 초기 최대 1,000개 항목을 기본값으로 제안하고 초과 시 범위 축소 또는 확대 확인을 받는다.

동기화는 사용자 요청 또는 업무 정리 실행 전 수행한다. 외부 서비스에 공개 webhook 수신 서버를 요구하지 않는다. 가능한 조건부 요청과 페이지네이션을 사용하며, `Retry-After`·호출 제한 응답을 존중한다. 무한 재시도나 다수 병렬 요청은 피한다. [S6]

증분 갱신만으로 삭제·권한 회수까지 완전히 감지했다고 가정하지 않는다. 접근 오류는 즉시 사용 차단하고, 캐시된 항목은 정기 재검증 또는 원문 조회를 통해 상태를 확인한다.

### 12.4 후속 확장
P1에서 쓰기 ActionTools·MCP Adapter·추가 서비스를 검토한다. MCP 도구도 동일한 승인·입출력 검증 경로를 거치게 한다. MCP 명세는 도구 호출의 가시성과 사용자가 호출을 거부할 수 있는 통제를 권고한다. [S7]

### 13.3 신뢰 경계와 제한
정책 분류는 기본적으로 `local-only`와 `approved-external`을 사용한다. 미분류 자료는 local-only로 취급한다. 외부 전송에는 생성 모델뿐 아니라 임베딩·재순위 모델·진단 로그가 포함된다. 서로 다른 정책의 자료를 합치면 더 제한적인 조건을 따른다.

비밀값은 공식 SecretStorage와 비밀값 이름 참조를 사용한다. 이 API는 여러 플러그인이 이름으로 공유할 수 있는 중앙 저장소이며, 플러그인별 강제 격리나 저장 암호화 방식까지 보장한다고 표현하지 않는다. [S3]

Obsidian 플러그인은 앱이 가진 접근 수준을 상속하며 파일·네트워크 접근을 세밀하게 격리하지 못한다. 따라서 본 PRD의 정책 엔진은 Harness 내부 행동 통제이고, 악성 플러그인·운영체제 침해를 막는 경계가 아니다. [S4]

업무 자료는 조직의 사용·반출 정책에 맞는 경우에만 연결한다. 자동 민감정보 탐지로 완전한 유출 방지를 보장하지 않으며, 사용자 지정 범위와 목적지 제한을 기본 방어로 삼는다. v0.1 원격 텔레메트리는 비활성화한다.

## 14. 데이터 모델과 저장 정책

### 14.1 핵심 엔터티

| Job | id, version, trigger, timezone, skillRef, scope, output, enabled | 발생 시점의 정의 버전을 Run에 고정한다. |
| Run | id, jobId, occurrenceKey, state, policyVersion, budget, timestamps | 상태 변경과 실행 이력을 영속 보관한다. |
| ToolCall | id, runId, toolVersion, validatedArgs, status, resultRef | 실행 전 정책 판단과 실행 후 결과를 연결한다. |
| Artifact / ChangeSet | id, runId, target, baseHash, patchHash, expectedHash, outputKey | v0.1 ChangeSet은 파일 1개만 대상으로 한다. |

| Skill | id, version, manifestHash, instructions, schemas, tools | 버전과 도구 요구를 검증한다. |

### 14.2 원본 기준과 저장 위치
**Vault**는 사용자가 관리하는 업무 원본과 명시적으로 저장한 결과의 기준이다. **GitHub**는 외부 Issue·PR의 기준이다. **운영 저장소**는 실행·승인·정책·문서 ID의 기준이고, **검색 인덱스**는 재생성 가능한 파생 데이터다.

일반 설정은 플러그인 설정 저장 경로에 두되 비밀값 참조·매핑 같은 작은 설정만 보관한다. Run·색인·임시 근거는 기본적으로 Vault 밖의 기기 로컬 앱 데이터 경로에 둔다. 경로는 최초 설정에서 표시하고 사용자가 확인한다. 공유·동기화 폴더에 운영 DB를 두지 않는 것을 기본값으로 한다.

저장소는 `vaultId + deviceId`로 분리한다. 같은 Vault의 다른 기기 상태를 파일 동기화만으로 병합하지 않는다. DB 구현체는 G0에서 영속 트랜잭션·강제 종료·배포 호환 시험 후 확정한다. PRD 단계에서는 특정 벡터 DB나 네이티브 모듈을 필수로 고정하지 않는다.

### 14.3 보존·삭제·복구
메타데이터 중심 실행 로그는 기본 90일, 임시 근거·미저장 초안은 7일, 역변경용 스냅샷은 7일 보관한다. 사용자 저장 Markdown은 자동 삭제하지 않는다. 세 값은 사용자가 변경할 수 있고 UI에 현재 보존량을 표시한다.

자료 철회 시 논리 접근은 즉시 차단하고 다음 정리 작업에서 활성 저장소의 원문·벡터·파생 캐시를 제거한다. “지금 정리” 행동을 제공하되 OS 백업·외부 동기화본·저장장치 복구 영역까지 완전 삭제한다고 보장하지 않는다.

운영 DB가 손상되면 자동 초기화로 기록을 지우지 않는다. 원본 보존, 읽기 전용 복구 모드, 백업 복원 또는 색인 재구축을 제공한다. 자체 암호화를 구현하지 않은 저장 데이터의 평문 가능성과 OS 디스크 암호화 사용 필요를 고지한다.

## 15. 상태 전이와 실패 복구

### 15.1 Run 상태 모델
```text
QUEUED → PREPARING → RUNNING
RUNNING → SUCCEEDED                     (검색 답변만 생성)
RUNNING → WAITING_APPROVAL → APPLYING → SUCCEEDED
RUNNING → APPLYING → SUCCEEDED          (사전 허용된 새 초안)
PREPARING / RUNNING / APPLYING → FAILED 또는 BLOCKED
WAITING_APPROVAL → REJECTED 또는 EXPIRED
진행 중 취소 → CANCELED / 프로세스 종료 후 미완결 → INTERRUPTED
```
`BLOCKED`는 정책·원문 충돌·인증 등 사용자 조치가 필요한 상태다. 수정 후 재시도는 새 Run으로 생성하고 기존 Run과 연결한다. 승인 대기에서 초안을 편집하면 patchHash를 다시 계산하고 이전 승인을 무효화한다.

### 15.2 장애별 처리 계약
| 상황 | 처리 | 재시도·복구 규칙 |
|---|---|---|
| 생성·검색 네트워크 일시 실패 | 남은 예산 내 최대 2회 재시도 | 실패 범위를 기록하고 완료를 가장하지 않는다. |
| 토큰 만료·저장소 접근 불가 | 해당 Connector·Run 차단 | 인증 수정 후 사용자 재실행한다. |
| 승인 이후 원문 변경 | ChangeSet 적용 차단 | 원문을 다시 읽고 새 변경안·승인을 받는다. |
| 승인 만료 | Run을 EXPIRED로 전환 | 근거 최신성을 재검사해 새 Run으로 진행한다. |
| 적용 직전 프로세스 종료 | 의도 기록과 원문 비교 | baseHash와 같으면 미적용 상태로 확인한다. |
| 적용 직후 기록 전 종료 | expectedHash와 원문 비교 | 동일하면 적용 완료를 복구 기록하고 다시 쓰지 않는다. |
| 적용 여부 판단 불가 | INTERRUPTED 또는 BLOCKED | 사용자가 원문을 확인하기 전 자동 재적용하지 않는다. |
| 색인 손상·모델 교체 | 기존 원본은 보존 | 재구축 중 상태와 검색 제한을 표시한다. |

### 15.3 멱등성과 트랜잭션 경계
예약 중복 방지는 occurrenceKey, 출력 중복 방지는 outputKey, 쓰기 복구는 ChangeSet ID와 해시를 사용한다. 세 목적을 하나의 Run ID로 대체하지 않는다.

v0.1은 파일 한 개의 변경 단위만 지원한다. DB와 Vault 파일 사이에 단일 분산 트랜잭션이 있다고 가정하지 않는다. 적용 의도 기록 → 최신 원문 비교 → 파일 변경 → 적용 결과 기록 순서를 사용하고, 중간 종료는 결과 비교로 조정한다.

따라서 시스템 전체의 “정확히 한 번 실행”을 무조건 보장하지 않는다. 조회는 재시도할 수 있으며, 부작용은 중복 방지 키와 적용 여부 확인으로 통제한다. 새 파일 생성도 경로 존재 여부와 예상 결과를 확인하고 기존 파일을 덮어쓰지 않는다.

취소는 아직 시작하지 않은 호출을 막는다. 이미 외부 서비스가 수신한 요청이나 완료한 로컬 쓰기를 되돌렸다고 표시하지 않는다. 되돌리기는 현재 버전 확인 후 별도의 사용자 승인 작업으로 수행한다.

## 16. 논리 아키텍처와 확장 인터페이스

### 16.1 모듈형 모놀리스
```text
Obsidian UI / Commands
           ↓
Core: Run · Policy · Approval · Budget · ToolRegistry
  ├─ Agent: Model · Context · Memory · Skill
  ├─ Tasks: Trigger · Schedule · Queue
  ├─ Search: Ingestion · Index · Retrieval
  ├─ Connect: GitHub DataSource / 향후 ActionTools
  └─ Ports → Obsidian Adapter / StateStore / ModelGateway
```
다섯 제품 모듈과 공통 Core를 유지한다. 처음부터 별도 서버·마이크로서비스·다중 Agent를 만들지 않는다. 의존성 규칙은 “공통 계약에 의존하고 구현체는 앱 진입점에서 조립한다”이다.

### 16.2 핵심 인터페이스 계약
| 인터페이스 | 책임 | 금지하거나 분리할 것 |
|---|---|---|
| VaultPort | 허용된 문서 조회, 버전 확인, ChangeSet 적용 | Agent의 직접 파일 시스템 접근 |
| ModelGateway | Provider 호출, 전송 정책·토큰·취소 적용 | Agent·Skill의 임의 네트워크 요청 |
| RetrievalPort | 범위·정책을 반영한 Evidence 반환 | 답변 생성을 검색 구현에 하드코딩 |
| Connector | 인증된 자료 수집, 정규화, 동기화 상태 | GitHub 스키마를 Core 데이터 모델로 사용 |
| ToolInvoker | 스키마·정책·승인을 거친 실행 | Skill에 의한 권한 자동 부여 |
| StateStore | Run·Job·승인·적용 저널 영속화 | Vault 문서·파생 색인과 원본 역할 혼합 |

TypeScript를 기본 언어로 제안한다. `contracts`는 Obsidian 타입을 import하지 않는다. Agent·Tasks·Search 로직은 테스트용 Adapter로 실행 가능해야 한다. 직접 I/O를 허용하는 모듈 목록은 lint·코드 리뷰로 제한하되 이를 강제 보안 샌드박스로 설명하지 않는다.

### 16.3 권장 저장소 경계
```text
apps/obsidian-plugin     앱 조립, UI, 명령, 설정
packages/contracts      공통 타입·스키마·Port
packages/core           실행·정책·승인·도구·예산
packages/agent          모델·맥락·기억·Skill
packages/obsidian       Vault·Editor Adapter
packages/tasks         예약·큐·보충 실행
packages/search        색인·검색·Evidence
packages/connect       GitHub·추후 MCP
packages/storage       기기 로컬 상태·검색 저장 구현
skills/  tests/        기본 Skill·단위/통합/시나리오 시험
```
P1의 Companion Runner는 Core·Agent·Tasks·Search·Connect를 재사용한다. Runner가 계속 켜져 있어야 앱 종료 중 실행이 가능하며, 접근 가능한 자료만 처리한다. 미동기화 노트나 다른 플러그인의 런타임 기능까지 사용할 수 있다고 가정하지 않는다. 원문 쓰기는 기본적으로 재연결 후 플러그인이 버전 확인해 적용한다.

| NFR-05 · P0 | 재시작 후 운영 상태를 복구한다. | Job·승인 대기·적용 의도를 보존하고 실패 주입 시험에서 원문 손실이 없다. |

외부 모델의 응답 시간은 검색 엔진 시간과 분리한다. 질의 임베딩·첫 토큰·전체 답변·전체 Workflow 시간을 각각 수집한다. Provider 지연을 제외한 측정치를 전체 사용자 체감 시간이라고 표시하지 않는다.

### 17.2 품질·효용 검증 지표
| 지표 | 초기 목표 | 평가 방법 |
|---|---|---|
| 검색 Recall@5 | 80% 이상 | 한국어·영문·코드 질의 30개에서 주석된 관련 문서의 회수율 평균을 계산한다. |
| 업무 사실의 근거 충실도 | 95% 이상 | 20개 업무 질문 답변을 사람이 문장 단위로 근거와 대조한다. |
| 무근거 질의 유보율 | 100% | 의도적으로 답이 없는 질문 10개에서 이력·사실을 만들어내지 않는다. |
| 검토 후 사용 가능한 업무 초안 | 70% 이상 | 10근무일 동안 “약간 수정으로 사용/대폭 수정/폐기”를 직접 평가한다. |

수치는 개인 파일럿의 통과 기준이며 대규모 사용자 통계가 아니다. 품질 목표가 미달하면 모델·검색·범위를 조정하고 미달 항목을 공개한다. 도구 실행 횟수나 자동 생성 노트 수를 사용자 가치의 대리 지표로 단독 사용하지 않는다.

### 19.3 주요 위험과 대응
**데이터 유출**은 범위·목적지 분리와 파생 정책 상속으로 통제한다. **원문 훼손**은 변경 구역 제한·해시 검증·승인·복구 시험으로 통제한다. **범위 팽창**은 Skill 1개·GitHub 읽기·단일 파일 쓰기로 제한한다.

**한국어·코드 검색 품질**은 실제 질의 세트로 검증하고, **네이티브 의존성·앱 호환성**은 G0에서 먼저 시험한다. **앱 종료 중 예약 미실행**은 제한을 명시하고 P1 Runner로 해결한다. **플러그인 간 강제 격리 부족**은 내부 정책으로 해결된 것처럼 표현하지 않는다.

## 20. 구현 전달용 계약 예시

### 20.1 Skill manifest 예시
아래 예시는 형식과 필드 의미를 고정하기 위한 계약 초안이며, 바로 실행되는 SDK 설정 파일을 의미하지 않는다. 식별자·예산은 검증 단계에서 조정할 수 있다.

```yaml
id: daily-work-review
version: 0.1.0
inputSchemaRef: schemas/daily-work-review.input.json
outputSchemaRef: schemas/daily-work-review.output.json
instructionsFile: instructions.md
requiredTools:
  - search.query
  - vault.read
optionalTools:
  - github.readItems
  - vault.proposeChange
limits:
  maxModelCalls: 6
  maxToolCalls: 20
  activeTimeoutSeconds: 120
```
`requiredTools`·`optionalTools`는 필요 기능의 선언이지 권한 부여가 아니다. Skill 버전·manifestHash를 Run에 저장한다. 임의 문자열 실행이나 코드 다운로드 필드는 허용하지 않는다.

### 20.2 Job 계약 예시
```yaml
id: daily-work-review-weekday
version: 1
enabled: false
skillRef: daily-work-review@0.1.0
trigger:
  type: weekly
  days: [MON, TUE, WED, THU, FRI]
  localTime: '09:00'
  timezone: Asia/Seoul
missedRunPolicy: latest_once_within_24h
scopeRef: user-approved-work-scope
outputMode: propose-daily-section
approvalPolicy: every-existing-note-write
runnerMode: embedded
```
요일 배열은 내부 표현이다. v0.1 UI는 매일·평일 프리셋만 제공한다. 예시 09:00은 사용자가 확정한 예약이 아니며 `enabled: false`로 시작한다.

### 20.3 ChangeSet 불변 조건
ChangeSet은 `runId`, `targetUri`, `baseHash`, `patchHash`, `expectedHash`, `outputKey`, `sourceRefs`, `policyVersion`을 필수로 갖는다. 신규 파일의 baseHash는 “파일 없음”을 나타내는 명시적 값으로 구분한다.

승인은 patchHash와 policyVersion에 결합된다. 파일 경로·내용·근거 정책이 바뀌면 새 ChangeSet을 생성한다. 적용 직전 최신 원문을 읽고, baseHash가 맞을 때만 단일 파일 변경을 수행한다. 적용 결과가 expectedHash와 다르면 완료로 표시하지 않는다.

**구현 시작점:** G0에서 계약·저장·단일 파일 변경을 검증한 뒤, G1의 읽기 검색과 G2의 일간 정리 흐름을 연결한다. Agent의 자율성을 확대하기 전에 근거·승인·복구 경로부터 완성한다.

**[S1] Obsidian 공식 TypeScript API 정의**
[obsidianmd/obsidian-api · obsidian.d.ts](https://raw.githubusercontent.com/obsidianmd/obsidian-api/master/obsidian.d.ts)

**[S2] Obsidian 공식 플러그인 점검 가이드**
[Obsidian October plugin self-critique checklist](https://docs.obsidian.md/oo/plugin)

**[S3] Obsidian 공식 비밀값 저장 가이드**
